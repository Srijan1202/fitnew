## Findings

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | **High** | **Schedule → Weekdays crashed (500) for a plan with more than 6 sessions.** Editing a rest day adds exercises and makes it a session, so a cycle (or a week) can hold 7–14. `trainingDays` only knows 2–6. Using a shared code with 7+ sessions failed the same way, for weekday codes too. | **Fixed.** Core `weekdaysFor`: 7 sessions take every weekday, and more than 7 are refused (422 `too-many-sessions`). Using a code outside 2–6 sessions is a 422 (`sessions-out-of-range`). Tested in core and the API. |
| 2 | **High** | **Build with FITOS AI would likely fail on the real Gemini.** The server caps every answer at 2,048 output tokens and waits 25 s. A 5–6 day plan is about 1,400 tokens of JSON before any thinking tokens, after a prompt holding the whole exercise list. The scripted test model cannot show this. | **Fixed:** the builder asks for 8,192 tokens and 60 s (`AiRequest.timeoutMs`, new), and the app waits 150 s, enough for one retry. **Still to do:** a live call on the server after deploy, as for 5.5. |
| 3 | Medium | A shared cycle stored its on/off pattern, read back from the days. A rest day edited into a session broke it, so the copy came out different. | **Fixed:** the code stores the cycle's exact layout (which days are rest). Tested. |
